# 用与不用招投标搜索 MCP 的差别（大白话）

## 一句话结论

不用搜索工具，DeepSeek 只能分析你喂给它的文字；用了这个 MCP，平台才能在当下真正去找获授权的公开官网，先正向找“支持申报”的线索，再逆向找“可能推翻、修正或限制申报”的线索。

但它的产品是**待人工复核的证据台账**，不是自动核验通过。

## 不用搜索工具时，DeepSeek 真正能做什么？

能做：

- 读操作人粘贴的公开文本或虚构样例；
- 摘要和分类，比对公司名、项目名、金额、日期；
- 发现输入文本内部的矛盾；
- 生成核对清单。

不能做：

- 不会因为“接了 DeepSeek API”就自动打开政府网或采购网；
- 不知道今天官网上有没有这条公告；
- 不知道已有公告后来是否发了更正、终止、中止、暂停、废标或投诉处理；
- 不能证明粘贴文本来自哪个 URL，是否被删减、过期或改写；
- 不能凭模型记忆给出可追责的官方证据。

所以，没有工具时，DeepSeek 是“文本分析员”，不是实时联网取证员。

## “正向搜索”和“逆向复查”到底差在哪？

假设申报人说：“某公司中标了 A 项目，并已完成履约。”

正向搜索是沿着这个说法找支持线索：

- F01：项目编号/名称对应的中标、成交或结果公告；
- F02：项目+供应商/采购人+标包是否在同一记录里；
- F03：有没有合同、履约验收或验收公告。

逆向复查是专门问“这个说法后来有没有被改掉、推翻、暂停，或者根本是同名串项目”：

- R01：更正、变更、澄清；
- R02：终止、中止、暂停、废标、流标、取消、撤销/撤回、作废/废止、停止采购；
- R03：质疑、投诉处理/决定、监督检查、中标/成交/采购结果无效；
- R04：用供应商法定全称或统一社会信用代码反查项目/标包；
- R05：后续合同/验收、合同解除/终止、验收不合格、重新采购/招标。

两个方向缺一不可。只做正向，容易看到最早的“中标喜报”，漏掉后来的更正或终止；只做逆向，又没有基础身份链，容易把别的同名项目的风险套进来。

这个 MCP 把 3 次正向和 5 次逆向写死在服务端：先完成正向并冻结候选，再跑逆向。不是让 DeepSeek 自己决定“要不要复查”。

## 用了 MCP 后，多了哪些真实能力？

1. **真实搜索**：保留每个正向/逆向 query、查询时间、后端、候选标题、URL 和片段。
2. **受控读取原页**：遵守 robots 和安全限制，记录最终 URL、重定向、取页时间、正文片段和 SHA-256。
3. **结构化对账**：只从同页绑定项目名+编号的完整页观察标包、主体、金额和日期；不能拿一页的包1和另一页的包2供应商拼证据。
4. **定向风险信号**：风险词与插词变体必须和同页项目编号或名称锚点一起出现，才写入 `risk_signals`；仍须人工看上下文。
5. **缺口也留痕**：超时、403、robots 禁止、PDF、动态页、抓取预算用完、逆向零结果都会写清楚，不让模型补一个答案。
6. **永远强制人工闸门**：`manual_review_required=true`、`system_may_auto_approve=false`，不存在机器自动 pass。

## 仍然不能保证什么？

用了也不能保证：

- 搜索引擎收录了所有公告；
- 逆向搜索 0 结果就等于没有更正或投诉；
- 同一页出现公司名就表示该公司是中标人，而不是落标人、代理机构或其他角色；
- 同名项目、分包、联合体、母子公司、曾用名、金额口径自动匹配正确；
- 官网上的页面必然真实、完整、当下有效；
- PDF 扫描件、附件签章、JavaScript 动态页、登录页或验证码能被读取；
- 超过 8,000 字符的页面尾部已被看到；`content_truncated=true` 时必须人工补读；
- 内容哈希证明业务事实；哈希只能识别“这次抓到的这份字节”；
- 中标/成交等于合同已签、已履约、已验收或已付款。

**中标不等于履约。** 如果申报的是“已完成业绩”，必须继续核对合同主体、标包、金额、验收/履约记录与后续变更，不能拿一张中标公告代替。

## 为什么“有 URL”还是不等于“已核验”？

URL 只是地址，不是结论：

- 搜索结果摘要可能过期，原页已改或删；
- 官网页也可能是转载、新闻稿、候选人公示或无关页；
- 同项目名可能对应不同年份、地区、标段或公司；
- 页面存在不代表申报人在页面里的角色正确；
- 页面可能后来被更正、撤销或重新发布。

所以搜索结果只标 `candidate_unverified`，抓取成功也只标 `retrieved_not_verified`。这两个词都没有 `verified`。

## 使用前后的具体差别

| 方面 | 不用搜索 MCP | 使用双向复核 MCP |
|---|---|---|
| 现场演示 | 演示“分析粘贴文本” | 演示“服务端 3 正向→5 逆向→取页→风险/缺口→人工闸门” |
| 证据追溯 | 往往只有一段文字 | 有 run ID、服务/流程版本、输入/计划哈希、query、后端、时间、URL、重定向、正文哈希和失败 |
| 正反交叉 | 看模型是否自己想到 | 服务端固定执行，模型不能跳过 R01–R05 |
| 失败处理 | 模型容易继续推测 | 超时/robots/403/PDF/动态页/零候选原样记缺口，`no_candidate_observed` 不等于不存在 |
| 安全 | 没有出网风险，但容易假称已查官网 | 有域名授权、SSRF/DNS/IP、重定向、大小、超时、并发、限频和 robots 等出站控制 |
| 审批 | 系统没有取证闸门 | 固定 `system_may_auto_approve=false`，必须实名人员签核 |
| 部署 | DeepSeek API 即可 | 多一个 Python MCP；生产建议自管 SearXNG+另一逆向后端，并实现长期审计台账 |
| 成本 | 主要是模型 token/API | 增加搜索 API 或 SearXNG 运维、网络、存储和人工复核成本 |
| PDF/动态页 | 只能分析别人粘的文字 | 当前不读 PDF/OCR，不执行 JS；诚实记缺口 |

## 为什么不能说“全方位防止出错”？

政府项目确实需要可追责，但“可追责”不等于“系统绝不出错”。更负责的设计是：

- 把必须做的正向/逆向查询固定下来；
- 把原 URL、时间、哈希、失败和覆盖缺口原样保留；
- 不把“没搜到”翻译成“不存在”；
- 不把“风险词命中”翻译成“已证明违法”；
- 平台长期保存请求人、复核人、审批人、原始工具 JSON、版本、人工意见和签核时间；
- 人工复核关键公告、附件、标包、主体角色、金额口径和时间线。

MCP 给出单次取证台账字段，但不是长期不可篡改审计系统。那部分必须由平台实现。

## 现场演示怎么说才准确？

1. 用公开或虚构字段建立一个案件，展示项目名、编号、标包和主体；
2. 展示宿主确定性调用 `crosscheck_tender_information`，不是让模型随机决定调不调；
3. 展示 F01–F03 在前、R01–R05 在后；
4. 展示真实后端、查询时间、URL、抓取时间、哈希和候选/已取未核验状态；
5. 展示 `coverage`、字段观察、风险信号、失败/缺口；
6. 最后停在 `human_gate`，明确“不会自动通过”。

## 一句安全路演表述

> 系统会对获授权的公开官网执行服务端固定的正向发现和逆向风险排查，保留 URL、时间、哈希、覆盖缺口和失败原因，输出待实名人员签核的证据台账。

## 一句禁止表述

> DeepSeek 已全网自动核验并保证所有招投标业绩真实、合法、完整且已履约。

前一句和当前能力一致；后一句把“搜索、读取、留痕、辅助复核”夸大成“事实与法律保证”，禁止在路演、标书或产品页使用。
